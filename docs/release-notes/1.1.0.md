# 1.1.0

### Fixed

- **A root path (`/`) in the OpenAPI spec crashed discovery of every table in the catalog**,
  leaving the whole catalog with zero tables instead of just skipping that one endpoint. A root
  path now gets its own table (named from the spec's title), or is skipped with a log message if
  that can't be determined - the rest of the catalog is unaffected either way.

- **Object schemas with no declared `properties` crashed column extraction** (free-form/
  `additionalProperties`-typed objects, `allOf`-composed schemas, circular `$ref`s). Since the
  same pattern often recurs across many endpoints in a real spec, this could take every endpoint
  in a catalog down to zero columns, not just one. Such a field now becomes an opaque `JSON`
  column instead; if it's the top-level response shape, that endpoint is skipped with a log
  message rather than crashing the catalog.

- **Nested response fields always read back as `NULL`** for both plain `SELECT` queries and
  index-join lookups. They now read their actual value correctly.

- **A `JOIN` against a bulk-lookup endpoint always returned 0 rows if the request and response
  schemas used different casing for the same field** (e.g. request field `ip`, response field
  `IP`) - common, since the two schemas are authored independently and OpenAPI has no rule
  requiring them to agree. Practical effect: a bulk-lookup endpoint's join key column now reads
  as `ip`, not `request_filter_ip`, and a join like `ON postgres.ip = rest.ip` works as expected.

- **An optional request field declared using OpenAPI 3.1's `anyOf: [{type: X}, {type: null}]`
  nullable pattern silently vanished as a filter entirely** - not usable via `WHERE` or `JOIN`,
  with no error or warning. Such fields are now recognized and exposed as a filter like any
  other.

- **A JSON-shaped column (free-form/dictionary object, or a nested array) always read back as an
  empty string instead of its actual content.** It now reads back its real JSON content.

- **A non-equality `WHERE` on a bulk-lookup `JOIN`'s key column failed the whole query** (e.g.
  `WHERE ip IS NOT NULL`, or any range like `BETWEEN`) - even though the join worked fine without
  it. This was one of the most common patterns there is, e.g. after a `LEFT JOIN`. Such
  predicates are now evaluated normally instead of throwing.

### Changed

- **JSON-shaped columns are now Trino's real `JSON` type, not `VARCHAR`.** These columns now
  support Trino's JSON functions directly (e.g. `json_extract_scalar(col, '$.foo')`) without an
  explicit `CAST(col AS JSON)` first.
