# 1.2.0

### Fixed

- **A `JOIN` against a bulk-lookup table (for example `JOIN rest.default.enrich ON ...`)
  sometimes failed with a null-pointer and sometimes returned rows**, for the same SQL, same
  catalog, no schema change. Retrying the query was often enough to make it succeed. The join
  was running on whichever worker happened to hold the other side of the join; a worker that had
  not successfully loaded the API's OpenAPI spec at catalog start had nothing to look up against
  and crashed. The coordinator now sends the endpoint definition with the join itself, so a
  worker does not need its own copy of the spec to run the query.

- **`SELECT *` (or any scan) against a bulk-lookup table failed with a filter-POST error**
  about a missing resolvable predicate. That table is not filter-POST: there is no `WHERE`
  that makes a scan work, because keys come from a `JOIN`. The query now fails with
  `Table <name> can only be used in a join.` Filter-POST tables with a real missing `WHERE`
  still get the old missing-predicate message.

### Changed

- **The OpenAPI spec is no longer fetched when every Trino node starts the catalog.** Only the
  coordinator loads it, the first time it actually needs the table list (planning, `SHOW TABLES`,
  splits). If that fetch fails, the next such call tries again instead of leaving the catalog
  empty until a restart. Workers still call the target API to run the query; they just no longer
  need to fetch the spec to do it.

- **A large `JOIN` against a bulk-lookup table parsed each HTTP batch into one Jackson tree of
  the entire JSON array** before reading any columns. Peak heap and parse CPU grew with every
  field of every row in that batch, including columns the query did not select. The join now
  parses one response object at a time. The selected output cells for the current batch are
  still held until the batch is returned to Trino.
